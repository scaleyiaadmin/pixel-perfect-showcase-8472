Catálogo das APIs oficiais

Comunicação com as APIs

Protocolo: HTTPS (TLS 1.2 ou superior)

Método HTTP: POST

Formato do corpo: JSON UTF-8

Formato de data/hora: ISO 8601

Autenticação: OAuth2 (Password Grant Type)

Identificação da aplicação: api_key na query string

Domínio Oficial das APIs

Todas as integrações devem utilizar o domínio oficial:

https://api.antt.gov.br

Não é permitido o uso direto de IPs, hosts internos ou domínios alternativos.

Estrutura Base das APIs MONITRIIP

/monitriip/log/v1/<domínio>/<recurso>

/monitriip → identifica o sistema MONITRIIP

/log → APIs destinadas ao registro de eventos

/v1 → versão atual da API

/domínio → agrupamento funcional

/recurso → operação executada

Exemplo de Estrutura de Endpoint

HML: POST https://api-hml.antt.gov.br/monitriip/log/v1/<domínio>/<recurso>?api_key=<CLIENT_ID>
PRD: POST https://api.antt.gov.br/monitriip/log/v1/<domínio>/<recurso>?api_key=<CLIENT_ID>

Exemplo de Endpoint Real

HML: POST https://api-hml.antt.gov.br/monitriip/log/v1/bilhetes/venda?api_key=<CLIENT_ID>
PRD: POST https://api.antt.gov.br/monitriip/log/v1/bilhetes/venda?api_key=<CLIENT_ID>

Segurança das APIs

As APIs operam com dois mecanismos obrigatórios de segurança:

OAuth2 (Password Grant Type) – autenticação da aplicação

api_key – identificação da aplicação remetente

Processo de Onboarding Via Portal SISHAB

O onboarding garante que somente empresas autorizadas realizem chamadas às APIs Monitriip.

Atores

Transportador – empresa detentora da outorga ou serviço

Fornecedor de Tecnologia – provedor de soluções de TI (bilhetagem, telemetria, ERP etc.)

ANTT – órgão regulador e provedor de APIs

Portal SISHAB – sistema central de habilitação e gestão de credenciais

Etapas do Onboarding

Cadastro da empresa no SISHAB

Solicitação de habilitação para uso das APIs do Monitriip

Envio de informações técnicas (ambiente, tecnologia, responsáveis)

Análise pela ANTT (validade da relação fornecedor–transportador e aderência técnica)

Geração das credenciais  (As credenciais serão enviadas ao procurador responsável por e-mail, após o cadastro e a devida vinculação no sistema do SISHAB)

ClientId

ClientSecret

UserId

UserSecret

Scope

Liberação de ambiente de homologação

Homologação técnica – envio de eventos para cenários de teste acordados

Liberação de produção – após aprovação formal da ANTT

Obtenção de Token OAuth2

O token de acesso é obtido no provedor de autorização da ANTT.

Endpoint HML

curl -X POST "https://sso-hml.antt.gov.br/realms/ext-antt/protocol/openid-connect/token" \
-H "Content-Type: application/x-www-form-urlencoded" \
-d "grant_type=password" \
-d "client_id=<CLIENT_ID>" \
-d "client_secret=<CLIENT_SECRET>" \
-d "username=<USERID>" \
-d "password=<USERSECRET>" \
-d "scope=openid email profile"

Endpoint PRD

curl -X POST "https://sso.antt.gov.br/realms/ext-antt/protocol/openid-connect/token" \
-H "Content-Type: application/x-www-form-urlencoded" \
-d "grant_type=password" \
-d "client_id=<CLIENT_ID>" \
-d "client_secret=<CLIENT_SECRET>" \
-d "username=<USERID>" \
-d "password=<USERSECRET>" \
-d "scope=openid email profile"

Exemplo de Resposta do Token

{
  "access_token": "eyJhbGciOi...<TOKEN>...",
  "expires_in": 300,
  "refresh_expires_in": 0,
  "token_type": "Bearer"

Matriz de Erros de Segurança (Tipos Comuns)

 | 

 | Código
 | Situação
 | Como corrigir

 | 401
 | Token ou expirado
 | Obter novo token OAuth2

 | 403
 | Credenciais sem permissão para API
 | Ajustar escopo via SISHAB/ANTT

 | 400
 | Falha de validação nos campos de payload
 | Corrigir dados enviados

Boas práticas de Segurança

Armazenar clientSecret, UserSecret e ClientId em cofres de segredos (Vault, KMS etc.)

Não inclua segredos em logs, prints, e-mails ou sistemas de suporte

Renovar o token OAuth2 antes do vencimento

Nunca compartilhe credenciais entre diferentes empresas ou transportadores

Restringir a geração de tokens a serviços backend de confiança

Conectividade

Requisitos de Transporte

Protocolo: HTTPS obrigatório

Cifras: TLS 1.2 ou superior

Redirecionamentos HTTP → HTTPS não são garantidos

Uso sempre o endpoint HTTPS direto

Tempo de Resposta e Tempo Limite

Timeout recomendado do cliente: 30 a 60 segundos

Se ocorrer timeout sem resposta:

Registrador de incidente em log local

Verifique se o evento foi persistido no backend (quando houver recibo posterior)

Aplicar política de nova tentativa com backoff exponencial

Política de Retentativas (Repetir)

Pode  haver tentativa em:

Erros 5xx (falhas de infraestrutura)

Timeouts de conexão ou de resposta

Não deve haver nova tentativa automática em:

Erros 4xx (dados inválidos, autenticação, autorização)

Exemplo de recuo:

1ª tentativa → falha

2ª tentativa → após 30 segundos

3ª tentativa → após 60 segundos

4ª tentativa → após 120 segundos

Registros de Auditoria no Lado do Integrador

Cada sistema integrador deve registrar localmente:

Data e hora da chamada

Ponto final chamado

Corpo JSON enviado (mascarando dados sensíveis, se necessário)

Código HTTP da resposta

Corpo da resposta (recibo e mensagens)

API Gateway e Rotamento

Papel do API Gateway

O domínio https://api.antt.gov.br é exposto por um API Gateway responsável por:

Validar token OAuth2

Validar uma chave de API

Aplicar limites de taxa

Executar políticas de segurança (WAF, mitigação de ataques)

Roteamento interno para sistemas backend

Geração de medições e registros técnicos

Benefícios

Isolamento entre sistemas backend diferentes

Auditório completo por mas

Evolução de versões sem quebra de compatibilidade

Modelo de Resposta

Sucesso

Resposta retornada quando o evento é processado e registrado com sucesso pela API.

{
  "reciboEletronico": "82836b84-ad64-460b-123a-d2f98bb7c98f",
  "Mensagens": [
    {
      "codigo": "MSGA-10-SUC",
      "mensagem": "Log recebido com sucesso"
    }
  ]
}

Erro de Validação

Resposta retornada quando ocorre falha de validação no payload enviado.

{
  "reciboEletronico":"3a4a0585-69e3-41a3-123a-bc8b95b28beb",
  "Mensagens": [
    {
      "codigo": "MSGA-01",
      "mensagem": "Campo obrigatório cnpjEmpresaTransporte não preenchido"
    }
  ]
}

Boas práticas

Utilização do idLog somente para cada evento enviado.

Manter consistência entre eventos correlacionados (bilhetes, viagens, jornada e telemetria).

Não reenviar indefinidamente eventos que retornam erros 4xx .

Implementar retentativas ( retry ) apenas para erros 5xx ou timeout .

Proteger client_secret e api_key com rigor.

Realize a homologação completa antes da liberação em produção.

Versão e documentação das integrações internamente.
